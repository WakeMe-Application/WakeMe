v1.2 주요 변경 (2026-09-11) — iOS 우선 전환

  • 플랫폼 순서: Android 우선 → iOS 우선. 개발자 본인 기기(iPhone 17)로 매일 출퇴근길에 도그푸딩하고, 골든 라이드도 여기서 쌓습니다.
  • 핵심 신호: 정차 감지 + 시간 모델 + 실시간 열차위치 API. Cell ID는 Android 확장(Phase 3)에서 쓰는 보정 신호로 이동.
  • 신규 가설 H5: iOS 백그라운드 생존 — iOS 우선 전략의 Go/No-go.
  • 서버: 개인 MVP까지 불필요. 앱이 실시간 API를 직접 호출하고 Live Activity를 로컬로 업데이트합니다.
  • 신규: 13장 기술 스택, Phase 0 아이폰 로거 앱(PoC/WakeMeLogger)과 점검 스크립트.

v1.1 주요 변경 (2026-09-11)

  • 핵심 기술: Cell ID 단일 의존 → 센서 퓨전. iOS는 Cell ID 공개 API가 없어 v1.0 구조로는 구현 불가.
  • 위치 판정: Cell ID 정확 일치 상태머신 → HMM 확률 추론 + 예외 상태(반대 방향·지나침·불확실) 포함 상태머신.
  • 알림: 도착 시점 알림 → 전역 출발 시점(문 열림 60초 전) 기준 3단계. 이어폰 오디오·워치 채널 추가.
  • 데이터 모델: JSON 오류("mnc": 05) 수정, LTE/5G 필드(TAC·ECI·NCI) 반영, 노선 그래프/관측 모델 분리.
  • 크라우드소싱: [지금 내림] 버튼 라벨링 → 세션 종료 후 자동 시퀀스 라벨링.
  • 신규 섹션: 가설 검증, 경쟁 분석, 알림 설계, 플랫폼 제약, 성공 지표, 리스크, 로드맵, Non-goals, 오픈 이슈.

1. 개요

🎯 핵심 페인 포인트

  • 졸음으로 하차 역을 지나침 가설 H1
  • 노이즈 캔슬링·콘텐츠 몰입으로 안내방송 미수신
  • 혼잡 시 사람에 가리거나 꺼진 차내 전광판

👥 타겟 페르소나

  • 졸음 통근자: 장거리 출퇴근, 알람급 강도 필요
  • 노캔 몰입 유저: 이어폰 착용, 폰 진동을 놓치기 쉬움
  • 전광판 의존 유저: 청각장애인, 방송을 이해하기 어려운 승객

💡 핵심 가치 (USP)

시간표 추정이 아닌 실제 열차 위치 기반 알림 + 폰을 열지 않는 잠금화면 전광판 + 이어폰·워치로 전달되는 확실한 하차 신호

🧭 제품 원칙

  • 늦는 것보다 이른 게 낫다 — 미탐 1회가 신뢰를 무너뜨림
  • 확실한 척하지 않는다 — 추정 상태는 명확히 표시
  • 폰을 열지 않는다 — 잠금화면·이어폰·워치
  • 매일 0~1탭 — 루틴 기반 자동 시작

2. 문제 가설 & 검증 계획

아래 가설은 기획의 전제입니다. Phase 0(PoC)에서 검증하고, 결과에 따라 제품 정의와 우선순위를 확정합니다.

#가설검증 방법결과에 따른 결정
H1 역을 지나치는 1순위 원인은 몰입·전광판 가림보다 졸음이다 출퇴근 승객 설문(n≥200) + 심층 인터뷰 10명 졸음이 1순위면 알람형 알림(P2 → P1 상향)과 반복 알림 강화
H2 기존 앱의 하차 알림(진동, 약 30초 전으로 관찰)은 ① 지연·급행 시 부정확하고 ② 혼잡·노캔·졸음 상황에서 놓치기 쉽다 경쟁 앱과 동일 구간 동시 탑승 테스트 20회 이상 — 알림 발송~문 열림 시간, 진동 인지 여부 기록 오차가 작으면 차별점을 정확도가 아닌 리드타임·알림 채널로 집중
H3 정차 감지 + 노선 순서만으로 역 판별 정확도 97% 이상이 가능하다 아이폰 로거 로그를 정차 마크(정답 라벨)와 대조해 오프라인 분석 iOS 우선 전략의 핵심 가설. 미달 시 실시간 열차위치 API 비중을 높임
H4 지하 구간에서 셀과 역(구간)이 충분히 1:1에 가깝게 대응한다 Phase 3로 연기. 통신 3사 Android 단말 셀 로그 분석 (광중계기·누설동축 구간 포함) 식별력이 낮으면 Cell ID는 보정 신호로 한정
H5 iOS 백그라운드 생존: 백그라운드 위치(.otherNavigation, 자동 일시정지 끔)로 앱을 유지하면 잠금 상태에서도 센서가 끊기지 않고, 배터리는 시간당 5% 이하다 아이폰 로거 + check_ride.py (백그라운드 샘플 수집률 ≥ 95%, 1초 넘는 끊김 0건) iOS 우선 전략의 Go/No-go. FAIL이면 서버 주도(APNs) 구조로 바꾸거나 Android 우선으로 복귀

※ 기존 앱의 알림 방식(진동, 하차 약 30초 전)은 사용자 관찰(2026-09-11)이며, 앱별 차이와 정확한 시점은 H2 테스트로 확인합니다. 위치 추정 방식은 추정하지 않고 테스트 후 업데이트합니다.

시사점: 기존 앱이 "진동 1회 + 약 30초 전"이라면 ① 노캔·졸음 사용자는 진동을 놓치기 쉽고 ② 혼잡한 차내에서 30초는 문까지 이동하기 빠듯합니다. 깨워줘는 리드타임(≥ 60초)과 알림 채널(이어폰·워치·반복)로 차별화합니다.

4. 잠금화면 전광판 UX

사용자가 가장 먼저 알고 싶은 정보는 "지금 어디"보다 "몇 정거장, 몇 분 남았나"입니다. 예시 경로: 2호선 내선 강남 → 서초.

※ 소요시간·문 방향 등 목업 수치는 예시 데이터입니다.

표시 원칙

  • "이번 역" = 다음 정차역 (차내 방송 기준). 정차 중에는 현재 정차한 역을 표시합니다.
  • 1순위 정보는 남은 정거장 수와 예상 시간. 역 이름 3개 나열은 보조 정보입니다.
  • 추정 상태는 점선 테두리·"(추정)" 라벨로 구분합니다. 확실한 척하지 않습니다.
  • 표시 채널: iOS는 Live Activity·다이내믹 아일랜드(상시표시 지원 기기에선 화면을 켜지 않아도 보임), Android는 FGS 진행 알림(Android 16+ Live Updates ProgressStyle: 역 = 진행바 위 포인트).
  • 홈/잠금 위젯은 갱신 예산 제약으로 실시간 표시에 부적합합니다. 루틴 원탭 시작 버튼 용도로만 씁니다.

5. 핵심 UX 플로우

1

목적지 설정 (루틴 0~1탭)

요일·시간대 기반 출퇴근 루틴을 자동 제안합니다. 사용자는 목적지만 입력하고, 출발역은 지하 진입 직전 위치로 자동 추정합니다. 노선·방향(내선/외선, 상행/하행)·급행·지선·환승은 자동 계산합니다. 위젯·단축어(App Intents)로 원탭 시작도 지원합니다.

2

탑승 확정 & 방향 검증

승강장 대기(WAITING) 중 첫 출발이 감지되면 탑승을 확정합니다. 첫 역 변화가 경로와 반대면 즉시 반대 방향 경고를 보냅니다. 붐벼서 열차를 한 대 보내도 다음 열차로 자연스럽게 이어집니다.

3

잠금화면 전광판

폰을 열지 않고 잠금화면만 봐도 남은 정거장·예상 시간·신뢰도를 확인할 수 있습니다.

4

3단계 하차 알림

준비(2역 전 출발) ➔ 하차(전역 출발, 문 열림 60초 이상 전) ➔ 확인(도착 후 미확인 시 반복). 환승역에도 동일하게 적용합니다.

5

자동 종료 & 예외 처리

하차 후 보행이 감지되거나 GPS가 복귀하면 세션을 자동 종료해 배터리를 보호합니다. 지나쳤다면 다음 역에서 되돌아가는 방법을 안내합니다.

6. 알림 설계

도착(문 열림) 시점 알림은 혼잡한 차내에서 문까지 이동할 시간이 없어 너무 늦습니다. 기존 앱은 하차 약 30초 전에 진동으로 알리는 것으로 관찰되는데(3장), 깨워줘는 2차 알림을 문 열림 60초 이상 전으로 잡아 두 배 이상의 여유를 확보합니다. 모든 알림은 문 열림 기준 리드타임으로 정의합니다.

단계트리거목표 시점기본 채널
1차 준비 목적지 2역 전 출발 도착 약 3~4분 전 짧은 진동 1회 + 이어폰 차임
2차 하차 목적지 전역 출발 문 열림 ≥ 60초 전 강한 진동 + 이어폰 TTS("다음 역 서초, 내리실 역입니다") + 워치
3차 확인 목적지 정차 감지 후 사용자 미확인 정차 즉시, 확인할 때까지 반복 알람형 (소리·진동 반복)
경고 반대 방향 탑승 / 목적지 지나침 감지 즉시 강한 진동 + 안내 화면
  • 1정거장 구간이면 1차를 생략합니다. 사용자가 알림을 앞당기도록 설정할 수 있습니다.
  • 위치 신뢰도가 낮으면(UNCERTAIN) 알림을 자동으로 앞당깁니다.

7-3. 위치 판정: HMM + 상태머신

  • 은닉 상태: 구간 s ∈ {역 i 정차, 역 i→i+1 주행}. 급행은 정차역 시퀀스로 구성합니다.
  • 전이: 노선 그래프 기반 단방향 진행 제약. 머무를 확률은 소요시간 분포에서 산출합니다.
  • 관측: 정차/출발 이벤트, P(셀 관측 | 구간), 실시간 열차 상태.
  • 알림 판정: P(목적지 전역 출발 완료) > τ. 사후확률이 분산될수록 τ를 낮춰 알림을 앞당깁니다.
IDLE ──[목적지 설정]──▶ WAITING (승강장 대기)
WAITING ──[첫 출발 감지]──▶ TRACKING (구간 i)
TRACKING ──[진행 방향 ≠ 경로]──▶ WRONG_DIRECTION   ⚠ 즉시 경고 + 경로 재계산
TRACKING ──[목적지 2역 전 출발]──▶ PREPARE          🔔 1차 준비
PREPARE ──[목적지 전역 출발]──▶ ALIGHT_NOW          🔔🔔 2차 하차 (문 열림 ≥ 60초 전)
ALIGHT_NOW ──[목적지 정차 감지]──▶ ARRIVED          🔔🔔🔔 3차 확인 (미확인 시 반복)
ARRIVED ──[보행 감지 / GPS 복귀]──▶ COMPLETED       세션 자동 종료
ARRIVED ──[미하차 상태로 재출발]──▶ MISSED           ⚠ 되돌아가기 안내

* 모든 추적 상태 ──[근거 부족]──▶ UNCERTAIN (시간 모델 폴백 · 알림 앞당김)
* 환승 경로: 환승역 ARRIVED ──▶ 다음 구간 WAITING 자동 연결
* 최대 세션 시간 초과 시 강제 종료

7-4. 데이터 모델

① 노선 그래프 — 공공 역코드 기반 정적 데이터. 앱 번들에 넣고 버전으로 관리합니다. (값은 예시)

{
  "graph_version": "2026.09.1",
  "line_id": "L2",
  "direction": "INNER",
  "stations": {
    "222": { "name": "강남", "transfer": [] },
    "223": { "name": "교대", "transfer": ["L3"] },
    "224": { "name": "서초", "transfer": [] }
  },
  "segments": [
    {
      "seg_id": "L2-IN-222-223",
      "from": "222",
      "to": "223",
      "run_sec": { "p50": 90, "p90": 120 },
      "dwell_sec_p50": 30,
      "door_side_at_to": "TBD"
    }
  ]
}

② 관측 모델 — 크라우드소싱으로 갱신하는 P(셀 관측 | 구간). 통신사·RAT별로 분리합니다. (값은 예시)

{
  "plmn": "45005",
  "rat": "LTE",
  "tac": 10234,
  "eci": 8921341,
  "pci": 211,
  "earfcn": 1350,
  "neighbors": [ { "pci": 87, "earfcn": 1350 } ],
  "seg_id": "L2-IN-222-223",
  "phase": "DWELL",
  "p": 0.82,
  "n_obs": 431,
  "last_seen": "2026-09-01"
}
  • plmn은 문자열: MNC의 선행 0을 보존합니다 (SKT 45005 · KT 45008 · LG U+ 45006). v1.0의 "mnc": 05는 유효한 JSON이 아닙니다.
  • LTE는 TAC + ECI(28bit), 5G는 TAC + NCI(36bit → Kotlin/Java Long). v1.0의 LAC는 2G/3G 개념입니다.
  • 이웃 셀은 전체 ID 없이 PCI/EARFCN만 오는 경우가 많아, 지문(fingerprint) 특징으로 사용합니다.
  • phase: DWELL(정차) / RUN(주행). 셀 경계는 역 경계와 일치하지 않을 수 있습니다.
  • last_seen 기준으로 시간 감쇠를 적용해 통신사 셀 재배치에 대응합니다.

7-5. 데이터 수집 전략

  • Phase A (PoC 정답 데이터): 테스터가 통신 3사 단말로 PoC 노선을 탑승하며 셀 + 센서 로그 + 수동 정차 마킹을 수집합니다. 모델 학습·검증용입니다.
  • Phase B (자동 시퀀스 라벨링): 세션이 정상 종료되면 관측한 셀 시퀀스를 정차 이벤트·노선 순서에 정렬(Viterbi)해 지나간 모든 구간을 자동 라벨링합니다. 사용자 액션은 필요 없습니다.
  • Phase C (품질 관리): 신뢰도 낮은 세션을 제외하고 이상치를 제거합니다. 셀 재배치가 감지되면 해당 구간을 재학습합니다.
v1.0 대비: [지금 내림] 버튼 시점은 이미 승강장·계단일 가능성이 높아 라벨 노이즈가 큽니다. 게다가 탑승 1회에 목적지 1개만 라벨링됩니다. 자동 시퀀스 라벨링은 탑승 1회로 전 구간을 라벨링합니다.

7-7. 프라이버시 설계

  • 온디바이스 추론 (iOS·Android): 이동 중 위치를 서버로 보내지 않습니다. 실시간 열차위치 API 호출에는 노선 이름만 들어갑니다.
  • 최소 전송 (공개 출시 후): 서버 프록시에는 구독할 노선만 보냅니다. H5 실패로 서버 주도 구조가 되면 출발역·방향·탑승 시각만 보내고 세션 종료 시 삭제합니다.
  • 크라우드 업로드: 세션 종료 후 (셀, 구간) 쌍만 집계해 업로드합니다. 기기 ID와 타임스탬프 시퀀스는 보내지 않고, 출발·도착 인접 구간은 제외해 집·회사 추정을 막습니다.
  • 법규: 위치정보법상 사업 등록·신고 대상 여부와 동의·약관·보관 의무를 출시 전에 법률 검토합니다 (오픈 이슈).

13. 기술 스택

기술스택은 기획서의 제약에서 거꾸로 정합니다. 이 앱은 화면이 적고, 가치는 백그라운드와 시스템 화면(Live Activity·알림·액션 버튼)에서 나오므로 네이티브로 갑니다. Flutter·React Native는 핵심 기능이 전부 네이티브 모듈이 되어, 네이티브 위에 한 겹을 더 얹는 셈이 됩니다.
